# Maintainer harness canary

The `OMA Maintainer Harness Canary` is a manual, read-only GitHub Actions experiment. Its restricted Claude CLI environment, permissions, limits, and stream parser are also reused by the production OMA process adapter. The canary workflow itself remains evidence-only and never grants production authorization or invokes the writer.

Production activation and rollback are documented in
[`maintainer-bot-architecture.md`](maintainer-bot-architecture.md). Canary
artifacts remain non-formal evidence and are never accepted as a production
proposal.

## Boundary

- OMA remains the control/orchestration and independent-review layer. A future deterministic finalizer remains the only component that may receive a repository-scoped GitHub App writer token and create a Draft PR.
- Claude Code runs only on a GitHub-hosted ephemeral runner. The workflow's Secret-bearing Bash copies the provider key into inherited file descriptor 3, unsets `DEEPSEEK_API_KEY`, and replaces itself with `exec env -i ... node`; therefore the long-lived host Node and its former Bash process environment do not contain the key. The CLI requires `--provider-key-fd`, reads one bounded single line, immediately closes the descriptor, and never accepts the key through argv, an environment variable, a named file, stdout/stderr, or an artifact.
- Before the Claude child is spawned and again before deterministic validation, the host asserts that its current environment and any supplied source environment contain neither provider credential names nor the raw provider value. Only the separately constructed Claude child environment receives `ANTHROPIC_AUTH_TOKEN`. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` and sandbox credential denies remove it from every Claude-spawned Bash, hook, and stdio MCP subprocess while leaving it available to Claude Code itself for model API calls.
- The workflow has only `contents: read` and `issues: read`; checkout uses `persist-credentials: false`. The canary never commits, pushes, comments, changes labels, or creates a PR.
- Issue and repository text are untrusted evidence. GitHub API data is written to a structured JSON file, parsed deterministically, and sent to the CLI over stdin without shell interpolation.
- The GitHub-hosted image is fixed to `ubuntu-24.04`; the workflow installs Claude's required Linux sandbox dependencies (`bubblewrap` and `socat`) before any provider credential is present. Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor, so the workflow loads the narrow `bwrap` profile recommended by Claude Code and Ubuntu: it grants only `/usr/bin/bwrap` the `userns,` permission and does not apply to commands inside the sandbox. The workflow asserts that the global `kernel.apparmor_restrict_unprivileged_userns=1` restriction remains enabled before and after loading the profile. Claude Code is pinned to `2.1.220`, runs in bare headless mode with isolated `HOME`, `XDG_CONFIG_HOME`, and `CLAUDE_CONFIG_DIR`, and uses no user/project settings sources, session persistence, auto memory, plugins, MCP servers, Chrome, Web Search, Web Fetch, or nonessential telemetry/update traffic. A trusted `--settings` file outside the checkout and artifact directory makes sandbox availability mandatory, forbids unsandboxed fallback, disables sandbox auto-approval, and uses an empty strict network allowlist.
- The model has no Bash or Write tool. `Read` is limited to the checkout, and exact `Edit(path)` rules cover only `request.allowedPaths`; Read/Edit deny rules also cover `/proc`, the isolated control/home directory, and the artifact directory. After a full canonical command-policy comparison, focused validation is launched only through the fixed Bubblewrap boundary described below; the host never executes a validation command directly.
- DeepSeek is configured through its official Anthropic-compatible endpoint, `https://api.deepseek.com/anthropic`, with `deepseek-v4-flash` selected for the main and fallback model aliases.

The official references for these settings are the [Ubuntu 24.04 release notes on unprivileged user namespace restrictions](https://discourse.ubuntu.com/t/ubuntu-24-04-lts-noble-numbat-release-notes/39890#unprivileged-user-namespace-restrictions-15), [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference), [Claude Code permissions](https://code.claude.com/docs/en/permissions), [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing), [Claude Code environment variables](https://code.claude.com/docs/en/env-vars), [DeepSeek Claude Code integration](https://api-docs.deepseek.com/quick_start/agent_integrations/claude_code), [DeepSeek Anthropic API compatibility](https://api-docs.deepseek.com/guides/anthropic_api), and [GitHub Actions secure use reference](https://docs.github.com/en/actions/reference/security/secure-use).

## Evidence contract

The runner does not persist Claude Code message content or reasoning. It converts the raw stream into JSONL records containing only event sequence, type, and subtype. After the harness exits successfully, deterministic code rejects a moved base SHA, dirty initial checkout, commits, untracked files, deletion, rename, copy, conflict, type change, symlink, out-of-scope path, too many files, oversized file, or oversized diff.

Registered validation runs outside the model process but is still untrusted code. It starts only after Claude has exited, after the host/source credential invariant is checked again, and through a fixed `/usr/bin/bwrap` launcher. Deterministic host code creates a disposable validation snapshot from the pinned tracked Git base, removes its remote, and applies the exact binary candidate diff already captured after scope validation. Host ignored and untracked files are not copied. The original candidate checkout remains immutable evidence and is not mounted into the validation sandbox.

The launcher creates new user, PID, network, IPC, and UTS namespaces; mounts a new `/proc`; and leaves only the isolated network namespace's loopback with no host or external network route. Deterministic host code generates an exact `127.0.0.1 localhost` hosts file and a `hosts: files` NSS policy inside the validation container directory, verifies both before use, and mounts only those two files read-only as `/etc/hosts` and `/etc/nsswitch.conf`. It never mounts the host `/etc` or `/etc/resolv.conf`, so local test-server resolution does not introduce DNS or an external route. The disposable snapshot is writable at `/workspace` so tools such as Vite may create and remove required sibling temporary files, while its `.git` metadata and the host-installed `node_modules` tree are over-mounted read-only. Workspace dependency symlinks must resolve back into the disposable `/workspace/packages/*` tree. `/usr` and the active Node toolchain remain read-only, and `/tmp`, `/home`, and `HOME` are private tmpfs-backed mounts. The launcher begins with `--clearenv` and injects only fixed non-credential runtime variables plus exact policy-approved non-credential variables. The runner's original checkout (apart from the read-only dependency subtree), control directory, artifact directory, other `RUNNER_TEMP` contents, GitHub command files, and host home are not mounted. Temporary write access therefore carries no GitHub credential, provider Secret, network route, host-checkout authority, or artifact authority. Bubblewrap absence or launch failure produces `VALIDATION_SANDBOX_UNAVAILABLE`; there is no host-execution fallback.

The workflow installs Bubblewrap, loads the `/usr/bin/bwrap`-specific AppArmor profile, and runs the same sandbox builder's preflight before the provider Secret is introduced. Preflight proves that a Vite-style sibling temporary file can be created and removed inside a disposable snapshot, workspace dependency symlinks stay inside that snapshot, and `localhost` resolves only to a loopback address while the host candidate checkout remains untouched. A nonzero preflight emits one bounded, redacted JSON diagnostic with a stable reason code, exit code, safe OS error code, and sanitized stdout/stderr; it never falls back to host execution. The request must match complete policy-derived command objects exactly, including order, executable, arguments, repository-contained cwd, timeout, environment, and unset environment. All policy commands run sequentially against one disposable snapshot. After validation, deterministic code verifies the snapshot's HEAD, changed path set, file types, sizes, resolver files, complete filesystem manifest, and exact binary diff before cleaning it in a `finally` path. The immutable original checkout independently receives the existing final HEAD, path, type, size, and exact-diff checks.

Bubblewrap is launched without a shell by a dedicated bounded process runner, not the repository's general command runner. `maxValidationOutputBytes` is a combined stdout-plus-stderr raw-byte ceiling enforced while chunks arrive; multibyte text is counted by bytes, not JavaScript characters. Crossing the ceiling immediately discards captured output, sends SIGTERM to the detached bwrap process group, escalates to SIGKILL after a short grace period, and resolves through a final convergence timer even if a child ignores signals. The wall-clock timeout uses the same TERM-to-KILL path. These failures produce generic `VALIDATION_OUTPUT_LIMIT` or `VALIDATION_TIMEOUT` artifacts and never retain or echo the overflowing output.

The artifact directory must be empty after Claude, before and after validation, and before host output is written. A successful run can contain only host-created regular `events.jsonl`, `change.patch`, and `result.json` files. Unexpected files, directories, or symlinks cause `ARTIFACT_CONTAMINATION`; the whole contaminated directory is moved out of the upload path and replaced with a fresh directory containing only a safe `FAILED result.json`. Before writing any patch or event artifact, deterministic code scans the diff, safe events, validation evidence, and result for the raw provider credential.

A successful artifact contains the base SHA, `canarySnapshotRevision`, exact allowed and changed paths, validation evidence, duration, turn count, termination reason, patch hash, safe-event hash, and a canonical artifact hash. `canarySnapshotRevision` hashes the exact canary Issue fields and included material comments; it is deliberately not the production Maintainer Host authorization revision. Every artifact states `authority: canary_evidence_only` and `productionAuthorization: false`.

The parser accepts a turn count only from the official terminal `num_turns` field. It does not infer aliases or derive turns from the number of stream events. A successful result requires a native JSON number that is finite, a safe integer, nonnegative, and no greater than the configured `maxTurns`; `--max-turns 20` remains a hard CLI argument. Missing, `null`, string, boolean, object, array, fractional, unsafe, negative, and over-limit values all fail closed. The first-party Agent SDK 0.3.220 result type requires numeric `num_turns`, while the CLI contract defines `--max-turns` as the limit on non-interactive agentic turns; an observed runtime mismatch is therefore diagnosed, not normalized or treated as evidence that the field was renamed.

Expected fail-closed paths—including missing/nonzero/timed-out CLI, malformed output, scope violations, validation failure, and credential detection—write a strict `FAILED` `result.json` with stage, reason code, sanitized message, snapshot/base/path metadata, nullable turn/termination fields, safe event/validation metadata, and a canonical artifact hash. Unsafe patch, transcript, reasoning, absolute paths, and secrets are not retained. Artifact upload warns instead of replacing an earlier setup error when no file exists.

Turn-count failures use stable reason codes: `TURN_COUNT_MISSING` for an absent official field; `TURN_COUNT_TYPE_INVALID` for any non-number JSON type; `TURN_COUNT_NON_INTEGER` for non-finite, fractional, or unsafe numeric values; `TURN_COUNT_NEGATIVE` for negative safe integers; `TURN_COUNT_LIMIT_EXCEEDED` for a successful result above the configured limit; and `TURN_LIMIT_REACHED` only for the official terminal subtype `error_max_turns`. General stream-shape failures such as malformed JSON, no terminal result, or multiple result events remain `MALFORMED_OUTPUT`.

A turn-count failure may add `turnCountDiagnostic` containing only `resultEventSeen`, `fieldPresent`, a restricted `jsonType`, `numericClass` (`within_limit`, `max_plus_one`, `above_max_plus_one`, or `not_applicable`), and `configuredMaxTurns`. It never stores the exact over-limit value, an unknown field, terminal payload, result text, cost/token payload, transcript, or reasoning. The field is optional so existing v1 artifacts remain parseable. When present it is part of the same canonical artifact-hash input, and the existing credential/redaction checks still cover the complete artifact. Parser failure still quarantines any artifact contamination and writes only a safe `FAILED result.json`, never a patch or event file.

All canary output remains untrusted. A future promotion or fresh-checkout finalizer must re-enter the production outer admission, material snapshot/revision, claim, base-SHA, idempotency, path, validation, GitHub App identity, and Draft-only checks; it must never treat the canary snapshot hash as writer authority.

The FD/process and validation-sandbox contracts are covered by portable strict-mock tests plus Linux-workflow static assertions. On macOS the tests do not claim to execute Bubblewrap: the injected test process runner can only observe the fixed Bubblewrap invocation and simulate sandbox results; the production CLI exposes no sandbox-runner override. GitHub-hosted run [31525092429](https://github.com/open-multi-agent/open-multi-agent/actions/runs/31525092429) confirmed that the original preflight exited nonzero before the request/model steps, but the old generic error discarded Bubblewrap's stderr. Run [31599406585](https://github.com/open-multi-agent/open-multi-agent/actions/runs/31599406585) later confirmed the AppArmor/Bubblewrap preflight and a real Claude Code 2.1.220 plus DeepSeek `deepseek-v4-flash` terminal success, then failed closed during deterministic validation because Vite could not create its sibling config bundle on the former read-only `/workspace` mount. Run [31613510018](https://github.com/open-multi-agent/open-multi-agent/actions/runs/31613510018) confirmed the writable disposable snapshot, scope check, `git diff --check`, and a parsed `num_turns: 18`, but the focused Vitest startup failed closed with `getaddrinfo EAI_AGAIN localhost` because the isolated root had no resolver files.

Run [31620178408](https://github.com/open-multi-agent/open-multi-agent/actions/runs/31620178408), pinned to base `a294d52605e879fe82f0fa35d9a2e500a6212245` and Issue #491 snapshot `6607ad00bd70e085f0b56c1652eae9b02dd335005731d056dd864414a5ec8b8d`, confirmed the resolver preflight, Claude Code 2.1.220 process exit 0, one terminal result, and a successful terminal shape before the old parser rejected the turn count as `harness_output/MALFORMED_OUTPUT`. The uploaded failure artifact passed schema and canonical-hash verification and contained no transcript, reasoning, or Secret. Because the raw terminal event was intentionally not persisted, the run does not reveal whether `num_turns` was missing, the wrong JSON type, non-integer, negative, or above 20. The new reason codes and bounded diagnostic distinguish those cases in future evidence without widening retention. Local fake-CLI, strict-mock, and workflow-static tests for this parser change are not evidence of live provider behavior; a new live canary requires separate authorization.

The canary intentionally does not reproduce the Maintainer Bot's per-request token preflight. It uses wall-clock, max-turn, file-count, file-size, and diff-size limits instead.

## Supervised evaluation

Real runs require separate authorization because they execute a GitHub workflow and use a provider credential.

For the first 3-run canary, manually dispatch `maintainer-harness-canary.yml` three times against Issue #491 at the same current `main` and unchanged canary snapshot. Record each run ID and artifact hash. A run passes only if it completes within 30 minutes, stays within 20 turns, changes only `packages/core/tests/subpath-exports.test.ts`, passes the focused test and `git diff --check`, contains no secret/reasoning/raw transcript, and produces a patch whose hashes and metadata reverify. Any credential exposure, scope violation, malformed artifact, stale base/snapshot, nondeterministic patch, or missing validation is a fail-closed result.

For a 10-run replay, use ten clean checkouts pinned to the same base SHA and the same saved structured Issue snapshot. Run with a mocked provider first to verify the host boundary, then—only with separate authorization—run the real provider replay. Report success rate, median and p95 duration, median and p95 turns, patch equivalence or semantic equivalence, validation pass rate, fail-closed rate, and any secret/scope findings. Do not promote the harness unless at least 9 of 10 runs produce an acceptable patch, all 10 preserve security boundaries, all successful artifacts reverify from a fresh checkout, and no run requires a broader path or GitHub permission.

Promotion is a separate design and authorization decision. It must preserve the current outer admission, durable claim, base SHA and Issue revision checks, idempotency, path policy, GitHub App identity verification, fresh-checkout finalization, and Draft-only writer.
